## Problem Statement

AGXCLI (`agx`) installs a pinned `agent-plugins` release, bootstraps deployment-owned `agent-control`/`agent-contracts` GitHub repos plus a GitHub Project from clean templates, activates Codex/Claude, and tracks state via local non-sensitive receipts to reach a reserved `verified` state once external evidence is confirmed. It deliberately refuses to be a task orchestrator. Open question: is this worth building as a standalone product, or does it stay an internal tool for the founder's own fleet?

No checkpoint/resume: a late-stage failure (specifically netbird join) currently forces redoing the entire deployment from scratch, not just the failed step.

## Cross-Model Perspective

Independent cold read (Claude subagent, Codex unavailable — 401 auth error, `codex login` required):

- **Steelman:** AGX is the verifiable provisioning substrate for agent fleets — turns "stand up a new deployment" from a manual, half-day, error-prone ritual into an idempotent, receipt-backed operation that only claims `verified` once external evidence confirms the fleet member is real and usable. It's the attestation layer orchestration platforms currently assume away.
- **Key insight:** The single most revealing line wasn't the "delays our cluster" quote — it was **"netbird错一次要重来"**. This says the failure mode isn't "install broke" (AGX already handles that well), it's that **any late-stage failure nukes the entire deployment back to zero**. That's not a scope gap, it's an **architecture gap**: AGX's `apply`/`init` flow has no checkpointed/resumable state machine. The product isn't "install more things," it's "make provisioning idempotent so a step-N failure doesn't cost steps 1 through N-1."
- **Premise challenged:** Premises 1+5 combined — "underserved market layer" vs. "generic infra tooling (Terraform/Ansible/cloud-init + Tailscale ACLs) already solves 90% of this, founder just hasn't adopted it." Evidence that would prove the subagent right: hand the exact 3-4-deployment/netbird-redo problem to a DevOps engineer with a day and standard IaC, no AGX — if they replicate idempotent-resume behavior, AGX's value is "founder skipped standard infra hygiene," not a product gap. Evidence that would prove it wrong: that attempt fails specifically because the `agent-plugins`/`agent-contracts`/GitHub-Project/evidence-profile shape is bespoke enough that generic IaC can't express it without becoming AGX anyway.
- **Prototype suggestion (48h/1 engineer, informational only — not committed scope until Approach C's validation completes):** `agx bootstrap` as a checkpointed, resumable state machine — persist per-step success to a state file (extend existing receipt schema), resume from first non-succeeded step on re-run, add `netbird-reachability/v1` evidence profile modeled on `github-delivery/v1`. Test against 2 real pending deployments, killing netbird mid-join on one to confirm resumability. Skip: Multica execution evidence, any GUI, cross-platform beyond Windows/Ubuntu, general network/ACL management.

## Approaches Considered

### Approach A: Minimal patch — netbird-specific resumability
Add a state-checkpoint layer to `apply`/`init` scoped to the netbird step only, plus `netbird-reachability/v1` evidence profile. S/M effort, low risk. Fast to ship, tests directly against the real fleet — but the resumability logic is a one-off patch, not reusable for future steps.

### Approach B: Architectural — general checkpoint/resume in metadatafile
Make step-checkpointed resume a general capability of the receipt/metadatafile layer, not netbird-specific. M/L effort, medium risk. Closes the architecture gap the cross-model read identified for good — any future evidence profile or capability inherits it. Slower to ship; premature if premise 5 doesn't hold up.

### Approach C: Validation spike — test premise 5 before writing product code
No product code. Recruit a DevOps engineer, uninformed about AGX, give them one workday with Ansible + existing `netbird` CLI + Tailscale-style ACLs (no AGX) to replicate idempotent, resumable provisioning against the founder's real 3-4-deployment / netbird-redo problem. Replication succeeds → AGX's current value is "founder skipped standard infra hygiene," not a product gap — stays internal or gets shelved. Replication fails **because resumability itself couldn't be achieved** → the `agent-plugins`/`agent-contracts`/GitHub-Project/evidence-profile shape is genuinely bespoke; proceed to A or B with confidence. A failure caused by something else (a bug in the engineer's own playbook, unrelated tooling trouble) doesn't count either way — discard and re-run rather than treating it as a verdict. S effort (one person-day, no internal product-engineering time — the contractor fee itself is a real, separate cost, budget capped at founder's discretion), low risk. **Result is directional evidence, not proof** — one engineer, one day, is a small enough sample that a fail could mean "the shape is bespoke" or just "one day was too short" / "this engineer wasn't strong at Ansible." Treat a fail as evidence toward bespoke-ness, not as settled fact; a second independent engineer's attempt would raise confidence if the result is close.

**Choosing between A and B if replication fails:** a fail alone doesn't pick between the narrow patch (A) and the general architecture (B). Route to A if the engineer's failure was isolated to the netbird step specifically; route to B if their failure (or AGX's own future needs) implicates more than one step needing resumability — i.e., B is justified once a second capability needs the same checkpoint/resume behavior, not preemptively.

## Recommended Approach

**Approach C.** Both A and B commit engineering time to a premise (real market gap, not just founder's own missing infra hygiene) that has active, unresolved cross-model doubt. C spends one person-day instead of engineering weeks to convert premise 5 from a guess into evidence, and the result deterministically routes to A or B. Founder confirmed this choice directly.

## Success Criteria

Approach C succeeds as a validation step (regardless of which way the result points) if: a DevOps engineer with 3+ years' Ansible/Terraform experience, unfamiliar with AGX, given one 8-hour workday (access provisioned and scoped *before* the clock starts, so onboarding doesn't eat into the working window) and only Ansible/netbird CLI/Tailscale-style ACLs, attempts to reproduce idempotent resumable provisioning against at least 2 of the founder's real pending deployments (matching the low end of the founder's quantified 3-4-deployment scope — enough for one clean run plus one injected-failure run) — deliberately killing the `netbird` client process mid-join on one (the direct analog of the founder's original "netbird错一次" failure, not a physical network cut) — and the pass/fail of that reproduction, defined as *re-running after the kill only re-executes the netbird-join step, not the prior plugin-install/repo-bootstrap/Project-creation steps, verified by comparing captured task-run logs (e.g. Ansible `-vvv` output saved to file for both runs) before and after*, is recorded as directional evidence on premise 5. **The founder adjudicates the verdict directly from the captured logs, not from the engineer's self-report.**

Note: the engineer defines their own step decomposition in their own IaC implementation — it does not need to match AGX's internal step names, only the observable property (a mid-step kill doesn't force redoing already-completed steps).

**Safety:** the netbird-kill injection runs against a real pending deployment, not a throwaway sandbox — before running it, snapshot or otherwise ensure the deployment can be torn down and re-provisioned cleanly if the kill leaves it in a broken state; the engineer's access is scoped least-privilege and revoked at end of day regardless of outcome.
